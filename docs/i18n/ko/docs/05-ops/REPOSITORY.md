# 저장소 운영

이 문서는 커밋으로 추적되는 qhud 워크플로와 커밋 없이 바뀔 수 있는 GitHub 설정을 구분합니다. 저장소, `main`, 릴리스 태그 규칙은 **2026-09-15**에 GitHub에서 읽었습니다. 보안 기능, Actions 설정, `release` 환경, 경고 0건은 **2026-09-14**에 마지막으로 확인했습니다. 설정이 바뀐 뒤에는 다시 확인하세요. 현재 qhud는 기본 브랜치가 `main`인 **1인 유지관리 공개 저장소**입니다. 아래 비공개 저장소 열은 가시성이나 팀 규모가 바뀔 때 선택할 운영 방식이며 현재 설정을 설명하지 않습니다.

## 실제 협업 상황에 맞는 규칙 선택

| 항목 | 1인 비공개 | 팀 비공개 | 공개 qhud(현재) |
| --- | --- | --- | --- |
| 공개 범위와 접수 | 소스와 운영 이슈를 소유자에게만 보입니다. 내부 이슈 목록과 비공개 보안 신고 채널을 씁니다. | 필요한 최소 저장소 권한만 부여합니다. 내부 이슈와 비공개 보안 신고 채널을 씁니다. | 소스와 일반 이슈를 공개합니다. 영어·한국어·중국어로 구체적인 이슈와 PR을 받고, 의심되는 취약점은 비공개 신고로 보냅니다. |
| `main` 변경 | PR, 일곱 상태 검사, 검토 대화 해결, 선형 이력, squash 병합을 유지합니다. 필수 승인 0건이면 단독 관리자가 검사 통과 후 병합할 수 있습니다. | PR과 검사를 유지하고 독립 승인 1건 이상을 요구합니다. 코드 소유자 검토와 마지막 push 승인도 검토하고, 독립 릴리스 승인자를 둡니다. | 활성 규칙은 PR, 엄격한 일곱 검사, 검토 대화 해결, 선형 이력, squash 병합을 요구합니다. 관리자가 한 명인 동안 승인 요구는 0건이지만 검사는 면제되지 않습니다. |
| 릴리스 | 태그 생성과 게시를 소유자에게 제한하고, 공유 전에 노트와 산출물을 확인합니다. | 태그·릴리스 권한을 지정된 관리자에게 제한하고 독립 릴리스 승인을 요구합니다. | `v*` 태그를 보호하고 품질 게이트와 `release` 환경을 거쳐 게시합니다. 게시 전 릴리스 초안을, 게시 후 여섯 자산(아카이브 2개, SBOM, 각 체크섬)과 출처 증명을 확인합니다. |
| 보안과 경고 | 저장소 요금제에서 사용 가능한 GitHub 보안 기능을 확인합니다. 경고를 비공개로 검토하고 테스트에 실제 비밀을 복사하지 않습니다. | 경고 분류·수정 담당자를 정하고 보안 PR을 독립 검토합니다. | 비공개 취약점 신고, 의존성·코드 검사, 비밀 검사와 push 보호를 유지합니다. 새 경고의 악용 세부 사항을 공개 이슈에 쓰지 않습니다. |

기능 가용성, 비용, 독자를 확인하지 않고 공개 저장소 설정을 비공개 저장소에 그대로 복사하지 마세요. 두 번째 관리자가 생기면 검토자와 릴리스 승인자 역할을 먼저 정하고 시험 PR로 새 규칙을 충족할 수 있는지 확인한 뒤 승인 정책을 바꿉니다.

## 현재 브랜치·태그 보호

활성 [Protect main 규칙](https://github.com/chquandogong/qhud/rules/23268129)(ID `23268129`)은 기본 브랜치에 적용됩니다. 삭제와 강제 갱신을 막고, 선형 이력과 PR을 요구하며, PR 병합은 **squash**만 허용합니다. 검토 대화 해결과 작성자를 알 수 없는 변경에 대한 추가 승인도 요구합니다. **필수 승인 검토는 0건**이고 코드 소유자 검토나 마지막 push 승인은 의무가 아닙니다. **우회 권한자는 없습니다.** 필수 상태 검사는 엄격 모드여서 병합 전에 PR 브랜치를 최신 `main`에 맞춰야 합니다. [Protect release tags 규칙](https://github.com/chquandogong/qhud/rules/23267522)(ID `23267522`)은 `refs/tags/v*`에 적용되어 삭제, 갱신, 강제 갱신을 막고 우회 권한자가 없습니다. 이 규칙들은 GitHub 설정이므로 저장소 파일만으로 강제할 수 없습니다.

GitHub는 현재 squash 병합만 허용하며 자동 병합과 브랜치 갱신을 제공하고, 병합 후 PR 원본 브랜치를 삭제합니다. [CODEOWNERS](../../../../../.github/CODEOWNERS)는 전체 변경과 `.github/`, `scripts/`, `src-tauri/`에 `@chquandogong`을 지정합니다. 소유자를 명시하는 파일이지만 현재 규칙은 코드 소유자 승인을 필수로 만들지 않습니다.

정확한 필수 상태 검사 이름 일곱 개는 다음과 같습니다.

1. `fmt · clippy · test · build`
2. `Windows MSVC · test · build`
3. `docs · release metadata`
4. `dependency review`
5. `Analyze (rust)`
6. `Analyze (javascript-typescript)`
7. `Analyze (actions)`

앞의 세 검사는 [CI](../../../../../.github/workflows/ci.yml)에서 나옵니다. Ubuntu 24.04는 Node 시스템 지표 테스트, Rust 형식 검사, 경고를 오류로 처리하는 Clippy, Rust 테스트, 릴리스 빌드를 실행합니다. Windows 2022는 범위를 제한한 의존성 패치로 테스트·빌드한 뒤 `Cargo.toml`과 `Cargo.lock`이 바뀌지 않았는지 확인합니다. 문서 무결성 작업은 [저장소 검사기](../../../../../scripts/check-repository.mjs)로 버전, 릴리스 메타데이터, 세 언어 문서의 파일 대응과 번역 사실, 로컬 링크를 확인합니다. CI는 `main` push, PR, 릴리스의 재사용 가능한 품질 게이트에서 실행됩니다. 2026-10-01부터([#15](https://github.com/chquandogong/qhud/issues/15)) `codex/**` 브랜치는 PR로만 검증하므로 브랜치 push가 두 번째 실행을 만들지 않습니다. 커밋마다 CI 실행은 하나이며, PR 번호 기준 동시성 그룹이 대체된 실행을 취소합니다. 리뷰 전에 CI가 필요하면 초안 PR을 여세요. 필수 검사 이름 7개는 바뀌지 않았습니다. push와 PR 이벤트에 브랜치 기준 동시성 그룹을 함께 쓰는 방식은 어느 이벤트의 실행이 남을지 시점에 따라 달라지므로 택하지 않았습니다. [의존성 검토](../../../../../.github/workflows/dependency-review.yml)는 PR에서 새로 추가된 중간 이상 심각도의 의존성이 있으면 실패합니다. Analyze 세 검사는 저장소에 추적되는 CodeQL 워크플로가 아니라 GitHub CodeQL 기본 설정에서 나옵니다. 마지막으로 확인한 설정은 Rust, JavaScript/TypeScript, Actions를 PR과 매주 검사했습니다. 필수 검사 이름이나 언어를 바꾸기 전에 CodeQL 구성과 실제 상태 검사를 함께 확인하세요.

## Actions, 의존성 관리, 보안

마지막으로 확인한 Actions 정책은 선택된 GitHub 소유 액션과 `dtolnay/rust-toolchain`, `Swatinem/rust-cache`를 허용했고, 타사 액션은 전체 커밋 SHA에 고정했습니다. 기본 워크플로 토큰은 읽기 전용이었습니다. 워크플로 파일도 권한을 좁게 선언합니다. CI와 의존성 검토는 contents 읽기, 릴리스 패키징은 출처 증명을 위한 `id-token: write`와 `attestations: write`를 추가하고, 게시 작업만 `contents: write`를 가집니다. 액션이나 릴리스 작업을 바꿀 때 저장소 전체 Actions 정책과 작업별 권한을 함께 다시 확인하세요.

[Dependabot 설정](../../../../../.github/dependabot.yml)은 Cargo 업데이트를 매주 월요일 09:00(Asia/Seoul), GitHub Actions 업데이트를 매월 09:00에 요청합니다. 생태계당 열린 PR은 최대 5개이고 minor/patch 변경을 묶습니다. 마지막으로 확인한 GitHub 설정은 Dependabot 보안 업데이트, 비공개 취약점 신고, push 보호가 있는 비밀 검사, CodeQL 기본 설정을 켰습니다. 이 서버 설정은 `dependabot.yml`과 별개입니다. **2026-09-14**에 확인한 저장소 보안 경고 대기열은 비어 있었습니다(**0건**). 날짜가 있는 관찰값이며 지금도 경고가 없다는 보장은 아닙니다. 새 코드·의존성·비밀 검사 경고에서 영향 버전과 실제 도달 가능성을 확인하고, 노출된 인증 정보는 즉시 우선 처리하며, 가린 수정 내용과 검증을 PR에 기록합니다. 조율된 공개 전에는 취약점 재현 방법을 공개하지 마세요. [SECURITY.md](../../../../../SECURITY.md)를 따릅니다.

## Rust 의존성 정책

[`deny.toml`](../../../../../deny.toml)은 qhud의 Rust 의존성 정책을 정의합니다. CI 작업 **`Rust dependency policy`**는 cargo-deny 0.20.2로 `Cargo.lock`에 대해 `cargo deny --locked check`를 실행합니다. cargo-deny는 워크플로에 SHA-256이 고정된 상위 릴리스 압축 파일에서 설치합니다. cargo-audit은 권고만 검사하지만 cargo-deny는 한 도구로 RustSec 권고, 라이선스, 금지·중복 크레이트, 의존성 출처를 모두 검사하므로 cargo-deny를 선택했습니다. 의존성 검토는 계속 PR이 새로 들여오는 의존성을 검사하고, 이 게이트는 릴리스 품질 게이트를 포함한 모든 CI 실행에서 고정된 전체 그래프를 검사합니다.

- **범위:** qhud가 배포하는 Linux x86_64와 Windows x86_64 대상, 기본 기능입니다. 다른 대상에서만 쓰는 크레이트는 범위 밖입니다.
- **권고:** RustSec 취약점은 모두 검사를 실패시킵니다. 유지보수 중단(unmaintained)과 건전성 결함(unsound) 공지도 그래프의 모든 크레이트에서 실패로 처리하므로, 새 공지는 조용히 수용되지 않고 검토됩니다. 회수(yanked)된 버전은 경고만 냅니다. 수용한 권고는 `deny.toml`에 ID와 이유로 적습니다. **2026-10-01** 기준 수용 목록은 RUSTSEC-2024-0429(glib 0.18 건전성 결함, GHSA-wrw7-89jp-8q8g, [#13](https://github.com/chquandogong/qhud/issues/13)에서 추적), RUSTSEC-2024-0370(같은 GTK3 스택의 유지보수 중단 `proc-macro-error`), RUSTSEC-2025-0075, RUSTSEC-2025-0080, RUSTSEC-2025-0081, RUSTSEC-2025-0098, RUSTSEC-2025-0100(`tauri-utils` → `urlpattern` 경로의 유지보수 중단 `unic-*` 크레이트)입니다. 수용 항목 가운데 취약점은 없습니다.
- **라이선스:** `deny.toml`에 나열한 허용적 라이선스(MIT, Apache-2.0, BSD-3-Clause, ISC, Zlib 등)는 모든 크레이트에 허용합니다. MPL-2.0은 수정하지 않은 간접 의존성 다섯 개, 즉 `cssparser`, `cssparser-macros`, `dtoa-short`, `selectors`, `option-ext`에만 허용합니다. 그 밖의 라이선스는 실패합니다.
- **출처:** 허용 레지스트리는 crates.io뿐입니다. 허용 Git 출처는 `https://github.com/chquandogong/qmonster` 하나이며, Git 의존성은 `rev`로 고정해야 합니다.
- **금지:** 중복 버전과 버전 없는 qmonster Git 요구 사항은 실패가 아닌 경고입니다. Tauri, GTK, windows-rs 그래프에는 qhud가 없앨 수 없는 중복이 있습니다.

권고 데이터베이스는 실행 시 공개 RustSec 저장소에서 가져오며, 이 작업은 인증 정보나 제공자 접근을 쓰지 않습니다. 따라서 의존성을 바꾸지 않은 PR도 새로 공개된 권고 때문에 실패할 수 있으며, 이는 의도한 동작입니다. 범위가 좁은 lockfile 업그레이드로 고치고, 쓸 수 있는 업그레이드가 없을 때만 이유를 좁게 적은 `ignore` 항목을 추가합니다. [실행 지침서](RUNBOOK.md#dependency-policy-exceptions)를 참고하세요. 이 작업은 아직 일곱 필수 검사에 들지 않습니다. PR에서 통과한 뒤 정확한 컨텍스트 `Rust dependency policy`를 `main` 규칙 집합에 추가하고, 이 문서의 필수 검사 목록을 갱신합니다.

## PR, 이슈, 릴리스 게시

PR 전에 기존 이슈를 검색하고 범위가 명확한 변경을 만듭니다. [PR 템플릿](../../../../../.github/PULL_REQUEST_TEMPLATE.md)은 관련 이슈 또는 생략 이유, 변경 후 동작, 실제 검증, 미검증 항목, 개인정보·보안 확인, 세 언어 문서 갱신을 요구합니다. 검토 대화를 해결하고 엄격 검사를 위해 브랜치를 갱신한 뒤 일곱 상태가 모두 통과했을 때 squash로 병합합니다. 자동 병합도 이 게이트를 우회하지 않습니다. 일반 버그, 기능 제안, 지원 질문은 버전과 환경을 받는 세 [이슈 양식](../../../../../.github/ISSUE_TEMPLATE/)을 사용합니다. 빈 이슈는 막혀 있고 선택 화면은 문서와 비공개 보안 신고를 연결합니다. Issues는 켜져 있으며 Wiki, Projects, Discussions는 꺼져 있습니다. 글을 올리기 전에 인증 정보, 계정 데이터, 로컬 경로, 화면을 가리세요. 공개 이슈는 재현 가능성, 지원 버전, 플랫폼, qhud와 상위 제공자 중 어느 쪽 문제인지로 분류합니다. 채널 선택은 [SUPPORT.md](../../../../../SUPPORT.md)를 따릅니다.

[릴리스 워크플로](../../../../../.github/workflows/release.yml)는 `v*` 태그에서 시작합니다. 사전 검사는 안정된 `vX.Y.Z` 태그, 일치하는 Cargo·Tauri 버전, 내용이 있는 버전별 노트, CHANGELOG 항목, 이미 `origin/main`에 포함된 태그 커밋을 요구합니다. 전체 CI를 품질 게이트로 호출하고 Linux x86_64·Windows x86_64를 패키징하고, 정확한 버전의 `cargo-cyclonedx`로 태그된 고정 트리의 CycloneDX SBOM을 만들며, 세 파일 모두에 SHA-256 파일과 빌드 출처 증명을 만듭니다. 정확히 여섯 자산과 체크섬을 검증한 뒤 `release` 환경에서 먼저 초안으로 게시합니다. 태그 조회는 초안을 반환하지 않으므로 릴리스 목록에서 초안을 찾습니다. 이미 공개된 릴리스는 교체하지 않고, 중복 초안 중 하나를 고르지 않으며, 기존 초안 자산의 바이트가 다르면 덮어쓰지 않습니다. 자산 검증 후 초안을 공개합니다. 마지막으로 확인한 `release` 환경은 관리자를 승인자로 요구했고, 1인 저장소를 위해 자체 승인을 허용했습니다. **2026-09-14에 릴리스 불변 설정이 활성화됐으며 이후 새 릴리스에 적용됩니다. 기존 `v0.7.1`에는 소급 적용되지 않아 API의 `immutable` 값이 `false`입니다.** 태그 보호는 이미 `v*` 참조의 수정을 막습니다. 운영 순서는 [실행 지침서](RUNBOOK.md#release-procedure)에 있습니다.

## 번역 유지 관리

번역 정책과 검토자 체크리스트는 [CONTRIBUTING.md](../../CONTRIBUTING.md#documentation-and-translations)에 있습니다. `docs · release metadata` 작업은 이를 두 단계로 적용합니다. 매 실행마다 각 영어 원문과 미러 사이의 ID, 날짜, 릴리스 버전, 펜스 코드 블록, 표 행, 제목을 비교합니다. PR에서는 두 번째 단계가 `--base origin/<기준 브랜치>`로 검사기를 실행하고, 변경된 영어 원문에 변경된 미러가 없으면 실패합니다. 단, PR 커밋 중 하나의 `Translation-Exempt: <path> <reason>` 트레일러가 그 경로를 지정하면 통과합니다. 두 단계 모두 기존 필수 검사 컨텍스트 안에서 실행되므로 규칙 집합은 바꾸지 않았습니다.

첫 시험 적용은 **2026-10-01**에 v0.7.2 릴리스 노트(`docs/05-ops/releases/v0.7.2.md`와 두 미러)로 진행했습니다. 기계적 비교에서 사실이 일치했고 나란히 읽은 결과 의미 차이도 없어 번역을 수정하지 않았습니다. 같은 파일을 영어로만 수정하자 기준 비교가 실패했고, 트레일러로 그 경로를 지정하자 통과했습니다. 관찰한 비용은 다음과 같습니다. 기준 비교를 포함해 62개 미러 전체를 확인하는 검사기 실행은 유지 관리자 워크스테이션에서 2초가 걸리지 않았고, 짧은 파일 세 개를 나란히 읽는 데 몇 분이 걸렸으며, 날짜를 포함하는 앵커 ID를 제외하자 첫 전체 비교에서 사실 불일치가 하나도 없었습니다. 검사는 의미를 판단하지 않으므로 각 언어에는 여전히 읽는 사람이 필요합니다.

## GitHub 또는 워크플로 변경 뒤 재확인

1. GitHub에서 저장소 메타데이터, 활성 규칙 둘, 병합 설정, Actions 권한, `release` 환경, CodeQL 기본 설정, Dependabot·보안 스위치, 현재 경고 대기열을 읽고 확인 날짜를 기록합니다. YAML 파일에서 서버 설정을 추정하지 않습니다.
2. 새 시험 PR이 생성한 상태 검사 이름·CodeQL 언어를 필수 목록과 비교합니다. 엄격한 브랜치 갱신, 검토 대화 해결, 병합 방식, CODEOWNERS, 새 승인 규칙을 단독 관리자가 실제로 충족할 수 있는지도 확인합니다.
3. 추적 파일을 변경했다면 `node scripts/check-repository.mjs`와 관련 CI 검사를 실행합니다. 릴리스 변경이면 태그 계보, 버전, 세 언어 노트, 초안 승인, 체크섬, 출처 증명, 지원 플랫폼에서 내려받은 자산까지 확인합니다.
4. 관찰한 설정, 근거 날짜, 의도한 정책과 활성 정책의 차이를 이 문서 및 영어·중국어 문서에 갱신합니다. 경고 수는 날짜가 있는 관찰값으로 취급하고 해결을 주장하기 전에 다시 확인합니다.
