## 사이클 1 — v0.1.0 (2026-08-05)

<!-- qhud:anchor -->
<a id="what-worked-keep-doing"></a>

### 잘된 점(계속할 것)

- **프레임워크보다 실험 먼저**: 20줄의 GJS 창으로 어떤 뼈대도 만들기 전에 유일한 존립 조건(Mutter가 XWayland에서 keep-below를 따르는가?)에 답했다. 실제 바이너리를 이용한 두 번째 실험에서 같은 메커니즘이 적용됨을 확인했다.
- **재작성보다 재사용**: qmonster가 이미 `lib.rs` + `NoopSink` + 인자 4개인 `Context::new`를 내보낸 덕분에 데이터 계층 전체를 별도 비용 없이 얻었다. 초기 제품 범위는 실제로 표현 계층에만 한정되었다.
- **동등성 픽스처로서의 데모 페이로드**: 하나의 산출물이 세 역할을 한다. 빈 상태 UX, 개발 미리보기(`app.js`의 브라우저 대체 경로), 시각적 동등성 회귀 기준이다.
- **실제 교차 검증**: Codex 검토가 쓰지 않는 생성 경로를 소스 수준에서 독립적으로 확인했고, 채택한 변경 네 가지(CV-1..4)를 제공했다. 사용량을 쓸 가치가 있었다.

- **포맷터 훅과 표 수정의 충돌**: 쓰기 후 훅이 Markdown 표를 다시 정렬하므로, 이후 `Edit` 앵커는 먼저 다시 읽어야 한다. 시정 조치: 추가용 앵커를 선호하거나 포맷된 파일을 수정하기 전에 다시 읽는다(사이클 도중 적용).
- **설정 필드 추측**: `config.mux.capture_lines`와 `config.tmux.capture_lines`를 혼동해 빌드를 한 번 더 수행했다. 시정 조치: 고정 리비전에 맞춘 연결 코드를 작성하기 전에 정확한 구조체를 grep한다(저렴하고 확정적).
- **출시 기간에 실제 tmux가 없었으므로**, FR-5의 실시간 경로는 관찰이 아닌 구성(프로브 + 타입)으로만 검증했다. DASHBOARD 작업 보드의 최우선 항목이며, 의도적으로 완료라고 주장하지 않았다.

## 사이클 2 — v0.1.1 → v0.3.x (2026-08-05 → 06)

<!-- qhud:anchor -->
<a id="what-worked"></a>

### 잘된 점

- **사용자 압박 속에서도 증거 우선 디버깅**: 이론보다 관찰 수단을 먼저 구축했기 때문에(제목 비콘 → stderr 추적 로그 → 컴포지터 경로 입력 주입), 모든 “아직 고장” 보고가 계측 한두 차례 만에 수렴했다.
- **사용자 비판을 설계 입력으로 활용**: “두 개 값이 서로 달라 의미가 없다”라는 의견에서 D-011(범위에 맞는 표시)이 나왔다. 대체한 목업보다 더 나은 제품이 되었다.

<!-- qhud:anchor -->
<a id="what-to-fix-next-cycle-1"></a>

### 다음 사이클에서 개선할 점

- **합성 검증의 맹점 때문에 세 번이나 잘못된 “수정 완료” 주장을 했다**(XTEST는 Mutter의 대상 선택을 우회한다). 시정 조치는 이미 적용했다. 상호작용에 관한 주장은 컴포지터 경로 입력 주입 또는 사람의 직접 조작으로 검증해야 한다(TEST_PLAN 프로토콜, R12).
- **플랫폼의 예약 사항은 조용히 문제를 일으킨다**: SIGUSR1(JSC) 세그멘테이션 오류, DING의 입력 가로채기, tao의 가상 프레임, 오래된 screenX/Y, proc-macro 자산 캐싱. 시정 조치: 모두 공용 `tauri-linux-pitfalls` 메모리와 D-008/D-010/D-012에 기록했다. 창/입력 코드를 수정하기 전에 함정 목록을 확인한다.
- **자기 자신과 일치하는 `pkill -f`가 작업 셸을 두 번 종료했다**. 대괄호 패턴(`[q]hud`) 또는 정확한 `-x`를 사용한다.

## 사이클 3 — v0.4.0 → v0.5.0 (2026-08-07 → 10)

<!-- qhud:anchor -->
<a id="what-worked-1"></a>

### 잘된 점

- **운영자의 제품 설명을 계획으로 삼았다**: “모든 계정과 작업공간을 한눈에, 명시적 새로고침, 웹을 다시 열 필요 없게”가 사이클의 여섯 작업 단위(추가 사용량, 영속화, 전체 새로고침, D-015 다중 계정, agy RPC, codex app-server)로 바로 이어졌다. 추측으로 기능을 만들지 않았다.
- **위임형 조회 경로(D-016)**: 공급자의 자체 프로세스가 응답하게 해(codex app-server, agy 루프백), 순수 HTTP로는 해결할 수 없는 두 문제인 토큰 갱신과 키링 저장 자격 증명을 qhud가 인증을 건드리지 않고 해결했다.
- **모든 파서와 병합 규칙을 테스트부터 작성**해 여러 출처의 병합을 정직하게 유지했다. attach_accounts 덮어쓰기 버그는 한 번도 화면에 나오기 전에 RED 테스트에서 발견했다.

<!-- qhud:anchor -->
<a id="what-to-fix-next-cycle-2"></a>

### 다음 사이클에서 개선할 점

- **새 데이터 출처를 추가할 때마다 D-011 위반이 반복된다.** 하루에 세 건, 모두 운영자가 발견했고 모두 같은 형태였다. 두 값에 이름 하나(쌍둥이 “weekly” 칩), 한 사실에 이름 둘(weekly와 7D), 한 사실에 행 둘(계정 행과 그 계정의 활성 작업공간). 일부는 이미 시행 중인 시정 조치: 새로운 모든 기간/풀/행은 범위 이름을 처음부터 끝까지 전달해야 한다. 표시 용어는 고정한다(5H/1D/7D/30D). `labels(...)` 추적 로그는 이제 렌더링된 게이지 레이블을 출력하므로, 다음 위반을 운영자의 눈에 의존하지 않고 stderr에서 볼 수 있다.
- **app.js에 기록된 NUL 바이트** 때문에 grep은 파일을 바이너리로 취급해 일치 결과를 조용히 비웠지만, node는 여전히 파싱했다. 시정 조치: 생성 키의 구분자는 일반 공백을 사용한다. 이제 “grep이 갑자기 아무것도 못 찾음”을 문자열 부재가 아닌 파일 손상의 증상으로 인식한다.
- **`cargo clippy`/`cargo test`는 디버그 바이너리를 갱신하지 않는다**. 검증 도중 오래된 `target/debug/qhud`가 이전 페이로드를 보고한 적이 있다. 시정 조치: `--dump`를 근거로 주장하기 전에 `cargo build`를 실행한다.

## 사이클 4 — 선택 기능의 긴 추적 (2026-08-11 → 14, v0.5.1)

<!-- qhud:anchor -->
<a id="what-worked-2"></a>

### 잘된 점

- **이론을 세우기 전에 계측하고, 그 결과에 따른다**: ptr: 캡처 단계 추적 로그가 “선택이 안 됨”에 관한 네 가지 상충 가설을 한눈에 정리했다. 모든 클릭이 도착했고, 어느 것도 타일 위가 아니었다. 실제 수정 두 가지(사용량 행 선택, 중복 고스트 리스너)가 나왔으며, 이것들이 없었다면 세 번째 원인도 찾을 수 없었다.
- **재시작 대신 고장 난 인스턴스에서 실험**: xwd 픽셀 해시로 멈춤을 입증했다(DOM 시계가 갱신되는 동안 프레임 바이트는 동일). 외부 크기 변경으로 흔들기 처방이 무효임을 입증했고(D-008), unmap/remap으로 복구를 입증했다. 각 실험은 잘못된 수정이 출시되기 전에 수정 유형 하나씩을 배제했다.
- **증상을 측정하는 편이 메커니즘 진단보다 효과적이었다.** 렌더러 계층에 대한 두 시도가 실패한 뒤, 픽셀 가드(자체 푸터를 해시하고 정지 시 복구)가 오후 한나절 만에 해당 버그 유형을 끝냈다. 처음 22 h 동안 실제 멈춤 3건을 사용자가 알아차리지 못한 채 복구했다.

<!-- qhud:anchor -->
<a id="what-to-fix-next-cycle-3"></a>

### 다음 사이클에서 개선할 점

- **운영자의 보고와 로그는 서로 모순되었지만 둘 다 맞았다.** “클릭해도 아무 일 없음” + “모든 클릭이 정상 동작으로 기록됨”이 바로 표현 화면 정지의 징후다. 다음에는 셋째 날이 아니라 가장 먼저 픽셀을 해시한다. 시정 조치: 확인 방법을 RUNBOOK 한 줄로 정리했고 가드가 상시 수행한다.
- **검증할 수 없는 완화 조치에 두 번 “수정 완료”라고 했다**(DMABUF 끄기, 합성 끄기). 유발 조건을 필요할 때 재현할 수 없었기 때문이다. 둘 다 몇 시간 안에 재발했다. 시정 조치: 유발 조건을 재현할 수 없으면 “완화 조치 배포, 검증 전”이라고 말한다. 유발 원인을 이해할 필요가 없는 감지+복구를 우선한다.
- **rAF는 화면 표시가 아니다.** 소프트웨어 렌더링에서는 아무것도 화면에 도달하지 않아도 rAF가 계속 호출된다. 이를 기반으로 한 JS 감시기는 실제 멈춤을 감지하지 못했다. 페이지 내부 신호로 창 자체의 가시성을 감시할 수는 없다.

## 사이클 5 — 이틀간 조용했던 ⟳ (2026-09-01 → 09-04, v0.5.3)

<!-- qhud:anchor -->
<a id="what-worked-3"></a>

### 잘된 점

- **배포된 진단 기능이 한 번 실행으로 문제를 찾았다.** `QHUD_EXTRA_DIAG=1 qhud --claude-usage`는 v0.5.0의 응답 형태에 관한 의문 때문에 만들어졌고, 이번에도 한 번 호출로 답했다. 두 하위 객체가 정상 출력되어 본문이 유효한 JSON임을 입증했고, 의심 지점을 “죽은 토큰 / 빈 본문”에서 “필드 하나의 타입”으로 옮겼다. 과거 질문을 위해 만든 진단 기능이 새로운 질문에서 가치를 입증했다.
- **부분 실패를 부분 실패로 유지해 위젯의 정직성을 지켰다.** 기본 계정 숫자는 이틀 전 값이었고, 사용량 영역은 날짜와 점점 늘어나는 경과 시간으로 그 사실을 보여 주었다. 화면을 비우거나 오래된 숫자를 현재 값처럼 표시하지 않았다. FR-20의 시점 표시와 D-015의 부분 오류 규칙 덕분에 이틀간의 장애가 잘못된 숫자가 아닌 불편에 그쳤다.
- **실제 본문 그대로 작성한 테스트.** 실패 테스트가 실제 09-03 응답이므로, 회귀 기준은 손으로 쓴 근사치가 아니라 현실에 고정되어 있다.

<!-- qhud:anchor -->
<a id="what-to-fix-next-cycle-4"></a>

### 다음 사이클에서 개선할 점

- **필드 이름 없는 “Did not parse” 때문에 이틀을 잃었다.** 사이클 3에서 Codex를 통해 이미 배운 교훈이었다(`a937a3b`: HTTP 200과 “no data” 보고가 버그 두 개를 가렸고, 본문 미리보기로 둘 다 진단). 그런데 Claude 경로에도 똑같이 단서 없는 오류를 배포했다. 시정 조치: 운영자에게 노출되는 모든 파싱 실패에 파서 자체 메시지를 포함한다(D-019). 일반화한 교훈은 **거부할 때는 무엇을 거부했는지 밝혀야 한다**이다. 이제 다른 조회 경로에서 내용 없는 `ok_or_else` 거부를 grep할 가치가 있다.
- **선택 필드 하나가 전체 응답을 실패시켜서는 안 된다.** 5h/7d 기간은 `used_credits`와 아무 관계가 없었지만 함께 사라졌다. 시정 조치: 의미상 정수인 전송 숫자는 관대한 리더를 거치며, 공급자 본문에 추가되는 새 필드는 이번 주 공급자가 원하는 어떤 형식으로든 표현될 수 있다고 가정한다.
- **문서의 현장 집계가 5× 뒤처져 있었다.** v0.5.2는 가드 초기 며칠의 기록을 바탕으로 “08-17까지 멈춤 4건”이라고 적었다. 저널 전체 범위(08-26 → 09-04)에는 21건이 있으며, 모두 remap으로 복구되었고 디스플레이 절전 뒤 수분 간격으로 몰렸다. 복구가 보이지 않아 아무도 알아차리지 못했다. 이것이 D-017의 목적이자, 자동 복구 하위 시스템의 카운터를 사람이 우연히 볼 때가 아니라 의도적으로 읽어야 하는 이유다. 시정 조치: 이제 집계를 DASHBOARD 행으로 관리한다.
