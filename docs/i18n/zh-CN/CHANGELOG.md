## [0.7.1] — 2026-09-11

<!-- qhud:anchor -->
<a id="intel-gpus-on-linux"></a>

### Linux 上的 Intel GPU

- 在 Linux 上测量 Intel GPU。i915 与 xe 驱动不提供 busy 百分比，因此状态条读取每个 GT
  的空闲驻留计数器，并以采样窗口内的补集作为利用率，按 Windows 引擎计数器相同的规则取
  最繁忙的 GT。显卡的首次读取为缺口，计数器重置同样保持缺口，而不是虚构的 100%。不显示
  显存：这些 GPU 使用 MEM 已经报告的共享系统内存。

v0.7.0 加入的 GPU 列在 Intel 显卡上没有任何 Linux 数据源可以填充。已经提供 busy
百分比的设备保持不变：amdgpu 继续使用 sysfs 值，NVIDIA 继续使用 NVML。已在
Ubuntu 24.04 上使用 Intel Arc（Meteor Lake，i915）验证，读数与同一窗口内独立计算的
rc6 驻留值完全一致。
参见 [0.7.1 发布说明](docs/05-ops/releases/v0.7.1.md)。

### 系统图表与关于

- 新增低调的底部图表，显示 CPU、内存、受支持的 GPU、物理磁盘 I/O 和网络
  吞吐量，每 2 秒采样并保留最多 60 秒历史。指标按钮可展开详情，默认区域保持小巧。

  不可用或预热中的值显示缺口，有效空闲值保持为零；长采样间隔或窗口显示状态
  变化后重置速率基线与历史。

  不扫描进程、不启动监控子进程，也不发送遥测。
- 条件支持 Windows WDDM GPU Engine 计数器以及 Linux AMD sysfs / NVIDIA NVML。
  每个采样会话保持一个选定适配器；显存详情取决于数据源，目前仅在 Linux 提供。

  [作者主页](https://chquandogong.github.io/CHENGHAO-QUAN/)和代码仓库。

## [0.5.3] — 2026-09-04

用量端点改变了一个数值的写法。qhud 因此两天都无法读取整个响应体。

<!-- qhud:anchor -->
<a id="fixed-1"></a>

### 修复

- **一个变成浮点数的传输数值导致每次 Claude ⟳ 都失败。** 自 2026-09-01 18:26 起，每次刷新都报告“usage response did not parse”，尽管 HTTP 状态为 200，且同一次点击中的 Codex 和 agy 获取均成功；用量条继续显示 08-31 19:00 的快照，日期标注正确，但持续了两天。通过运行随产品发布的诊断命令（`QHUD_EXTRA_DIAG=1 qhud --claude-usage`）找到了原因：响应体是有效 JSON，但 `extra_usage.used_credits` 现在以 `4997.0` 而非原来的 `4997` 传入，serde 不接受将浮点数赋给 `i64`——于是仅一个可选的回退字段就使整个响应失败，包括与它毫无关系的 5h/7d 窗口。同样的 4997 个最小货币单位在 `spend.used.amount_minor` 中仍以整数形式传入，这证明那里的浮点数表示最小货币单位，而非美元。语义上为整数的金额字段（`used_credits`、`decimal_places`、`amount_minor`、`exponent`）现在会将值为整数的浮点数读为对应整数；有小数部分的浮点数继续遵循既有的禁止猜测缩放比例原则，被丢弃——但两者都不再使整个响应体失败。已在线验证：小组件自身的 ⟳ 返回 `claude usage ok [default] (5h 49%, 7d 7%, 3 scoped)`，额外用量行保持完整，结果也已持久化到获取结果存储中。

<!-- qhud:anchor -->
<a id="changed-1"></a>

### 变更

- **用量响应体被拒绝时，现在会指出发生漂移的字段。** 过去的错误只有一句“usage response did not parse”——为此诊断了两天。现在会携带 serde 自身给出的字段、类型及位置消息。响应体包含账户 uuid 和电子邮箱；此消息从设计上就不会包含这两者：未知字段会在不设类型的情况下跳过，而每个有类型的字段都是数值、布尔值，或窗口/套餐字符串。HTTP 200 加上无法解释的“no data”曾掩盖两个 Codex 缺陷（`a937a3b`），如今 qhud 已不会再产生这种形式的报告。

<!-- qhud:anchor -->
<a id="noted-1"></a>

### 记录

- **画面守卫的实际工作量远超 v0.5.2 的记录。** 在 journal 完整覆盖的 2026-08-26 → 09-04 时段内，现场统计为：**检测到 21 次冻结、21 次 remap 修复、0 次重新执行、0 次用户可见事件**（v0.5.2 条目写的是截至 08-17 共 4 次，测量范围是守卫启用后的最初几天）。冻结会成簇出现——09-01 的三分钟内发生三次，09-04 的两分钟内发生两次——因此每次修复确实有效（修复阶梯从未升级），但显示器一旦休眠，底层停滞就会迅速复发。D-017 的检测并修复策略让这些问题对用户不可见；触发条件仍无法按需复现。
- `~/claude-personal` 中的额外账户仍返回 401：其令牌于 2026-08-17 过期，尚未有新的登录替换它。这与此次漂移无关，也从未隐藏默认账户的数值——部分失败始终保持为部分失败，符合 D-015 的要求。
- `tauri.conf.json` 自 v0.4.0 起一直保留 `"version": "0.4.0"`；现在再次与 `Cargo.toml` 同步。

## [0.5.1] — 2026-08-14

“选择不起作用”——借助新的输入面包屑，依次剥离出三个真实原因，最终定位到冻结的渲染器。

<!-- qhud:anchor -->
<a id="fixed-3"></a>

### 修复

- **显示器休眠后小组件的像素冻结**（这是操作人员每天早晨反复报告“选择不起作用”并每日重启的根源）。已在线证明：尽管 JS、输入和 IPC 都在运行，窗口 pixmap 在相隔数秒的采样间却保持字节级一致——卡片和行选择均触发了面包屑日志，获取请求也已发出，但操作人员从始至终看到的都是数小时前的一帧。由于触发条件（空闲熄屏 + 锁屏）无法按需复现，因此采用了多层修复：
  - `WEBKIT_DISABLE_DMABUF_RENDERER=1`（GPU 路径从启动时就已降级——出现 libEGL “DRI3 device” 错误）。单独设置它并不够：同一天空闲熄屏时冻结再次出现，且已确认 WebKit 子进程的环境中存在该变量。
  - `WEBKIT_DISABLE_COMPOSITING_MODE=1`——冻结实例显示 WebKit 的 VBlankMonitor 正在等待 DRM vblank，因此彻底移除线程化合成器的帧时钟。这个尺寸下的软件渲染毫无负担。可通过 `QHUD_KEEP_DMABUF=1`、`QHUD_KEEP_COMPOSITING=1` 选择退出这些设置。
  - 这两个环境变量单独都未被证明足够（两者同时设置后冻结仍复发），而 JS rAF 看门狗在一次真实冻结期间始终未能察觉——软件渲染将 rAF 与屏幕解耦。有效的是测量症状：**Rust 侧像素守卫**每隔约 28 s 对小组件自身窗口的一条像素带计算哈希（其中的页脚时钟每秒重绘）。连续两次采样相同 ⇒ 冻结 ⇒ 修复：先 unmap/remap（已在线验证，可让真实冻结实例恢复绘制；随后重新设置窗口层状态），若仍然静止，则带 `--respawned` 重新执行。启用时会向 stderr 写一行“frame guard armed”；每次检测和修复都会记录。小组件不再能够持续冻结——它会在一分钟内自愈，或明确说明无法自愈的原因。参考机器最初 22 h 的现场结果：三次冻结、三次 remap 修复、零次重新执行，操作人员未察觉任何一次。

- **用量条行现在可以选择。** 对操作人员反复报告的“选择没有反应”进行了在线诊断：新的 `ptr:` 面包屑显示每次点击都已送达——而且每次都落在用量条行上，这些行之前根本没有选择行为（支持选择的卡片并不是操作人员点击的位置；每天重启从来不是影响因素）。现在点击任意用量条行——账户、工作区或幽灵行——都会在行内展开详情：内容与悬停提示相同，而悬停提示在置于底层的窗口上几乎不起作用。
- **幽灵行上有两个完全相同的 pointerdown 监听器**，因此一次点击切换两次，视觉上毫无变化。现在由一个统一的用量条处理器负责 ⟳ 分发、幽灵行移除及行选择。
- **点击 codex 行不再触发网络获取。** 获取操作移至该行上显式的 ⟳ 按钮（与 Claude 和 agy 一致）——选择一行绝不能成为网络操作。`--fetch-codex` 不变。

- **注销/强制终止时窗口位置与大小丢失**：window-state 插件只在正常退出时持久化；现在由轮询循环每隔 30 s 保存一次几何状态检查点。
